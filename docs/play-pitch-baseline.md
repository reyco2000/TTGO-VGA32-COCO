# PLAY pitch baseline — v0.16.1

Every BASIC `PLAY` note, played on the board and measured at a PC, on 2026-10-13. This is the reference to compare against after any change to CPU speed, frame pacing or the audio path.

## How it was measured

- Firmware v0.16.1, 6809 CPU, Disk Extended BASIC. CoCo 3, then CoCo 2.
- `tools/play_pitch_sweep.py` read each note's delay value from the ROM on the board, started the ROM's own tone loop with it through the WiFi debug API, and asked `tools/frequency_meter_mcp.py` on the PC (board audio jack wired to its input) what it heard.
- Settings: 0.9 s wait after starting a note, 1.5 s capture.
- Interrupts were masked, so "expected" is the tone loop alone: `894886 / (4 × (26 + 8N) + 3)` for O1–O2 and `894886 / (4 × (25 + 5N) + 3)` for O3–O5, where N is the ROM's delay value. A real `PLAY` sits about 0.8 % lower.

To repeat it:

```
python tools/play_pitch_sweep.py --machines coco3,coco2 --json out.json
```

## Result

| Octave | CoCo 3: pitch error | CoCo 3: FPS | CoCo 2: pitch error | CoCo 2: FPS |
|---|---|---|---|---|
| O1 | -0.21 % to -0.06 % | 60.0–60.1 | +0.22 % to +0.30 % | 59.9–60.0 |
| O2 | -0.12 % to -0.04 % | 60.0 | +0.27 % to +0.32 % | 59.9–60.1 |
| O3 | -0.08 % to -0.04 % | 60.0 | -3.45 % to -2.95 % | 57.9–58.3 |
| O4 | -0.07 % to +0.03 % | 59.9–60.0 | -4.30 % to -3.39 % | 57.3–58.0 |
| O5 | -0.04 % to +0.03 % | 60.0–60.1 | -5.83 % to -4.37 % | 56.5–57.4 |

- **CoCo 3:** all 60 notes within 0.21 % of the expected value at 60 FPS, with no audio rate correction.
- **CoCo 2, O1–O2:** correct, at 60 FPS.
- **CoCo 2, O3–O5:** all 36 notes flat, from 3.0 % at O3 C to 5.8 % at O5 B. The frame rate falls to 58.3–56.5 FPS and the audio rate correction follows it, so the note is continuous but low. The break is at O3, where the ROM switches from its 16-bit delay loop to its 8-bit one (`DECA` / `BNE`, more instructions per second). The CoCo 2 cannot hold 60 FPS on that loop.
- **Target for the CoCo 2:** O3–O5 within a few tenths of a percent at 60.0 FPS, like the CoCo 3.

Offsets of 0.3 % or less are within what the method can cause: each note pauses the board briefly, which disturbs the audio queue, and the capture starts 0.9 s later. A slower two-note test (2.5 s wait, 3 s capture) read within 0.03 % on both machines.
